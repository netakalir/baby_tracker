# מסמך אפיון מוצר: אפליקציית מעקב ותכנון לתינוק

---

## 1. חזון המוצר

### מה הבעיה שאנחנו פותרים
הורים טריים מתעדים מידע על התינוק שלהם (שינה, האכלות, מצב רוח) במספר כלים מפוצלים - וואטסאפ למשפחה, פתקים, אקסל, אפליקציות גנריות שלא מתאימות לקצב חיים אמיתי. אין מקום אחד שמהיר להזנה, ויזואלי להבנה, ומשותף בין שני ההורים בזמן אמת.

### מה המוצר נותן (במשפט אחד)
כלי מעקב יומיומי לתינוק - מהיר בהזנה, ויזואלי בתצוגה, משותף בין הורים - בלי תיאוריות מסובכות ובלי "ניתוח AI" של התינוק.

### למי זה מיועד
- שני הורים (או יותר, כולל מטפלת) שצריכים לתעד ולראות נתונים משותפים על ילד אחד או יותר
- משתמש שרוצה תכנון פשוט (מתי הארוחה הבאה, כמה מלאי נשאר) - לא ניתוח עומק

## 2. עקרונות מוצר מנחים

| עקרון | מה זה אומר בפועל |
|---|---|
| מהירות הזנה | כל פעולת תיעוד - לחיצה אחת או שתיים, אין טפסים ארוכים |
| ויזואליות | גרפים, שעון יומי גרפי, צבעים - לא טבלאות מספרים |
| פשטות מעל "חוכמה" | אין "ניתוח פסיכולוגי" של התינוק, אין דרמטיזציה |
| שיתוף הוא ליבה, לא תוסף | כל הדאטה משותף בזמן אמת בין כל בני המשפחה המורשים |
| עיצוב מכוון | מראה מקצועי ומגניב, לא תבניתי - אך לא עמוס/מוסח |

## 3. פונקציונליות - מפת דרכים מלאה

### Phase 1 - MVP (ליבה)
| פיצ'ר | תיאור |
|---|---|
| מסך "היום" | שעון 24 שעות גרפי, עם עיצוב מותאם (gradient, לא ברירת מחדל) ואנימציית כניסה עדינה בלבד |
| הזנה מהירה | כפתורי 🍼 😴 🧷 😊, עם תמיכה בטיימר פעיל; פידבק אנימטיבי קצר ופונקציונלי בלבד בלחיצה |
| צפי האכלה הבאה | משלב ממוצע פערים אישי **+** טווח מומלץ לגיל (נשלף מהמקור של תאב התובנות, לא בקריאה חיה לכל הזנה) |
| מסך שבוע | גרף מעוצב ומרשים (לא ברירת מחדל) להאכלות/שינה |
| **תאב תובנות AI (חדש)** | 2-4 כרטיסיות תובנה בשפה פשוטה, משוות נתון אישי לעומת נורמה כללית לגיל (מעודכן שבועית, לא בזמן אמת) |
| השוואת ימים | בחירת **כמות ימים חופשית** (לא מוגבל ל-2) ותצוגה כ-small multiples / גרף משולב |
| ריבוי ילדים | בורר ילד אם יש יותר מילד אחד במשפחה |
| שיתוף הורים | כל הורה רואה/מזין מהמכשיר שלו, בזמן אמת |
| PWA | אפשרות "התקנה" למסך הבית בטלפון |

> **הוסר מ-MVP ועבר ל-Phase 3:** חיסונים - הורחב לטאב "בריאות" ייעודי (ראו למטה)

### Phase 2 - גדילה והתפתחות
- עקומות גדילה לפי תקן WHO (משקל/גובה/היקף ראש)
- מעקב אבני דרך התפתחותיות (התהפך, ישב, מילה ראשונה...) עם אופציה לתמונה

### Phase 3 - בריאות ולוגיסטיקה
**טאב "בריאות" ייעודי (חדש, מורחב):**
- לוח חיסונים לפי הסטנדרט הישראלי (צ'ק-בוקס)
- יומן תורים (טיפת חלב, רופא ילדים)
- תזכורות בדיקות גדילה תקופתיות (מתחבר לעקומות הגדילה מ-Phase 2)
- תזכורות מעקב התפתחותי לפי גיל

**לוגיסטיקה (טאב נפרד או חלק מהבריאות - להכריע בעיצוב מסכים):**
- מעקב מלאי חיתולים/פורמולה + התראת "נגמר בעוד X ימים"

### Phase 4 - כלים חברתיים/משפחתיים
- חלוקת משמרות לילה בין הורים + מעקב הוגנות
- מצב SOS - טיפים מהירים למצבים נפוצים
- סיכום יומי אוטומטי לשליחה בוואטסאפ
- מצב "מטפלת" - הרשאות מוגבלות

### נדחה במכוון לעתיד (לא בתכנון הקרוב)
- התראות push חכמות (למשל "המלאי נמוך")
- מצב אופליין עם סנכרון

### פיצ'רים עתידיים שהוגדרו ברמת עיקרון
- אינטגרציית Google Photos (Picker API) לשיוך תמונות לאבני דרך - דורש בחירה אקטיבית מהמשתמש בכל פעם, התמונות נשמרות באחסון עצמי תוך 60 דקות (Supabase Storage)
- פיצ'ר AI - לא הוגדר עדיין, לתכנון נפרד בעתיד

## 4. ארכיטקטורה וטכנולוגיה

### תרשים ארכיטקטורה כללי
```
┌─────────────┐                    ┌──────────────────┐
│   React     │ ──────────────────▶│     Supabase      │
│  (Frontend) │ ◀──────────────────│  Postgres+Auth+    │
│ TypeScript  │   קריאות ישירות     │  Realtime+Storage  │
└─────────────┘   ע"י Supabase SDK  └──────────────────┘
                         │
                         ▼
                ┌──────────────────┐
                │  Edge Function    │   ← חריג יחיד לעיקרון "בלי שרת"
                │  (תאב תובנות AI)   │     קריאה בטוחה לשירות AI/חיפוש
                └──────────────────┘     חיצוני, בלי לחשוף API keys
```
**החלטת ארכיטקטורה מרכזית:** אין שרת Backend עצמאי שאנחנו כותבים ומתחזקים. ה-frontend מדבר ישירות עם Supabase, וההרשאות/אבטחה מנוהלות ב-Row Level Security (RLS) ברמת מסד הנתונים. **חריג יחיד:** תאב תובנות ה-AI דורש Edge Function קטנה (פונקציית serverless מנוהלת ע"י Supabase, לא שרת שאנחנו מתחזקים) כדי לקרוא בבטחה לשירות AI/חיפוש חיצוני בלי לחשוף מפתחות API בצד הלקוח.

### עיקרון-על: סטנדרט איכות קוד
**לאורך כל הפרויקט, ללא יוצא מן הכלל:** הקוד חייב להיות מקצועי, עקבי, ולא מתפשר. כל משימה שמועברת ל-Claude Code צריכה לעמוד בקונבנציות מקובלות ובסטנדרטים גבוהים (naming, מבנה, טיפול בשגיאות, typing) - בלי "קיצורי דרך" למען מהירות.

### טבלת טכנולוגיות

| תחום | טכנולוגיה | תפקיד |
|---|---|---|
| Frontend Framework | React + TypeScript | בניית הממשק |
| Backend / DB | Supabase (Postgres) | מסד נתונים, Auth, Realtime sync |
| אחסון קבצים | Supabase Storage | תמונות (אבני דרך, בעתיד) |
| גרפים/ויזואליזציה | Recharts / D3.js | שעון יומי, גרפי שבוע |
| אנימציות | Framer Motion | "feel" חכם - מעברים, אפקטים בלחיצה |
| עיצוב | Tailwind CSS + shadcn/ui | מראה מודרני ועקבי, לא תבניתי |
| ניהול דאטה בצד הקליינט | TanStack Query (React Query) | caching, רענון אוטומטי, loading states |
| ולידציה | Zod | בדיקת תקינות נתונים בטפסים/הזנה |
| בדיקות | Playwright (E2E) | בדיקה אוטומטית שהמערכת עובדת |

| מוניטורינג שגיאות | Sentry (אופציונלי) | זיהוי תקלות בפרודקשן |
| ניהול קוד | Git + GitHub | בקרת גרסאות |
| כלי בנייה | Claude Code | סוכן AI שמבצע את הפיתוח בפועל לפי הנחיה |

## 6. ניתוח יתרונות וחסרונות

### 6.1 החלטה: Supabase (BaaS) במקום Backend עצמאי (Java/Spring)

| | יתרונות | חסרונות |
|---|---|---|
| **Supabase (הנבחר)** | מהירות בנייה גבוהה משמעותית; Auth+Realtime+Storage מובנים; tier חינמי נדיב; RLS נותן אבטחה ברמת ה-DB בלי קוד נוסף | תלות בספק חיצוני (vendor lock-in חלקי); SQL/RLS הוא תחום שאינו מוכר לנתנאל (לא Mongo); שליטה פחות גרנולרית מבק-אנד עצמאי; פחות "תרגול" של הסטאק שנתנאל עובד בו בעבודה |
| **Backend עצמאי (Java/Mongo)** | שליטה מלאה; תרגול ישיר של כלים שנתנאל מכיר מהעבודה; אין vendor lock-in | זמן בנייה ארוך משמעותית; יותר "חלקים נעים" לתחזק ולבדוק (auth, CORS, deployment כפול); יותר סיכון לטעויות כש-AI agent בונה זאת |

**מסקנה שהתקבלה:** מכיוון שהמטרה המוצהרת היא ללמוד לנהל AI agent (לא לתרגל Java/Mongo), Supabase מתאים יותר - פחות "רעש" טכני, יותר התמקדות בניהול.

### 6.2 החלטה: BaaS ישיר מה-Frontend, ללא שכבת Backend ביניים

| יתרונות | חסרונות |
|---|---|
| קוד פשוט יותר - רק frontend | לוגיקה עסקית מורכבת (אם תתפתח בעתיד) תהיה "תקועה" בצד הקליינט או ב-Supabase Functions, לא ב-service layer נוח |
| משימות קצרות וממוקדות יותר ל-Claude Code | אם בעתיד יידרש חישוב כבד (כמו AI feature עתידי) - יתכן שיהיה צורך להוסיף Edge Function או שכבת backend חלקית |

### 6.3 החלטה: מודל `events` גמיש (טבלה אחת) במקום טבלאות נפרדות לכל סוג אירוע

| יתרונות | חסרונות |
|---|---|
| שליפה פשוטה של "כל מה שקרה היום" בקריאה אחת | פחות "type safety" ברמת ה-DB (metadata הוא jsonb לא מובנה) |
| הרחבה עתידית (שדות חדשים) בלי migration | שאילתות על שדות ספציפיים בתוך metadata מורכבות יותר מעמודה רגילה |

### 6.4 כללי: יתרונות/חסרונות הגישה של "ניהול AI agent" (Claude Code) במקום כתיבת קוד עצמית

| יתרונות | חסרונות / סיכונים |
|---|---|
| פיתוח מהיר משמעותית; מתאים ללמידת כישור ניהולי חדש; פחות זמן ב"ניפוי באגים טכני" | תלות בבדיקה קפדנית של כל תוצר (האם זה עובד באמת, לא רק "מתקמפל"); סיכון לקוד לא עקבי/לא איכותי בלי supervision צמוד; דורש שהמשתמש ידע לכתוב הנחיות ברורות ולבדוק תוצאות גם בלי לקרוא קוד שורה-שורה |

## 7. סיכונים ונקודות לתשומת לב

1. **אבטחת RLS** - טעות בהגדרת policies יכולה לחשוף דאטה משפחתי לא רצוי. חובה לבדוק בפועל (לא רק "להניח שזה עובד") לפני שמוסיפים פיצ'רים.
2. **התלות בClaude Code** - כל משימה חייבת להיות ממוקדת ולהיבדק בנפרד, אחרת איכות הקוד תיפגע עם הזמן.
3. **Google Photos integration (עתידי)** - מגבלת 60 דקות על base URLs מחייבת טיפול נכון בהורדה/שמירה מיידית - אם יבוצע לא נכון, תמונות "ייעלמו".
4. **Vendor lock-in חלקי ב-Supabase** - מעבר עתידי לפלטפורמה אחרת ידרוש מאמץ הגירה (לא חסם, אך שווה לדעת).
